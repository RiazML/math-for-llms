# Data Mixture Optimization

> _"A data mixture is a prior over what the model should become good at."_

## Overview

Data mixture optimization treats corpus composition as a constrained optimization
problem over domains, objectives, and risk constraints. In an LLM training run, data is
not an inert pile of text; it is the empirical distribution that defines the examples,
losses, risks, and capabilities the model will see.

This section is written as LaTeX Markdown. Inline mathematics uses `$...$`, and display
equations use `$$...$$`. The goal is to connect data engineering decisions to
mathematical objects such as records $r_i$, token sequences $x_{1:T}$, filters $f(x)$,
hashes $h(x)$, mixture weights $\boldsymbol{\alpha}$, and empirical expectations.

The scope is deliberately narrow: this chapter owns the training-data pipeline.
Tokenizer design, GPU training systems, benchmark methodology, alignment objectives, and
production MLOps each have their own canonical chapters. Here we study the data objects
that those later systems consume.

## 1. Intuition

Intuition gives the conceptual and mathematical layer for data mixture optimization. The
local variables in this section should be read as pipeline objects: documents, records,
tokens, filters, weights, shards, and manifests.

### 1.1 Mixture weights determine model skill profile

Mixture weights determine model skill profile is part of the canonical scope of data
mixture optimization. We model the relevant object as a finite collection $\mathcal{D} =
\{r_i\}_{i=1}^n$ with record-level metadata $m_i$ and text or token content $x_i$. The
practical question is whether the transformation preserves the intended empirical
distribution.

A useful local invariant is:

$$
\text{valid}(r_i, \mathcal{S}) = 1 \quad \Longrightarrow \quad r_i \text{ can be consumed by the next pipeline stage.}
$$

For `mixture`, the invariant should be explicit enough that a checker can fail fast. If
the invariant is only written in a notebook comment or an engineer's memory, it will not
protect a long-running data build.

Examples:
- A small local experiment can store this object in memory; a frontier-scale run must store it as sharded, versioned, validated records.
- The mathematical object is simple, but the operational contract must survive restarts, parallel workers, schema changes, and audits.
- The notebook for this section uses synthetic data so the same ideas can be executed without external files.

Non-examples:
- A path on disk without a manifest is not a reproducible dataset.
- A metric dashboard without record-level lineage is not a provenance system.
- A filter threshold without an audit sample is not evidence of quality.

Implementation consequence: every transformation should report both a count and a rate.
If $n_{\mathrm{in}}$ records enter the stage and $n_{\mathrm{out}}$ records leave, the
acceptance rate is

$$
a = \frac{n_{\mathrm{out}}}{n_{\mathrm{in}}}.
$$

A sudden change in $a$ is a data-drift signal even when the code still runs. This is why
pipeline math is inseparable from logging, manifests, and audit slices.

For LLM work, the token-weighted view is often more important than the document-weighted
view. A filter that removes 5 percent of documents may remove 30 percent of tokens if it
targets long documents. The corresponding token acceptance rate is

$$
a_{\mathrm{tok}} = \frac{\sum_i f(r_i)\,T_i}{\sum_i T_i},
$$

where $T_i$ is the token count or a deterministic token-count estimate. The distinction
matters for compute budgets, mixture proportions, and scaling-law interpretation.

optimization. The local variables in this section should be read as pipeline objects:
documents, records, tokens, filters, weights, shards, and manifests.

### 3.1 Uniform by document

Uniform by document is part of the canonical scope of data mixture optimization. We
model the relevant object as a finite collection $\mathcal{D} = \{r_i\}_{i=1}^n$ with
record-level metadata $m_i$ and text or token content $x_i$. The practical question is
whether the transformation preserves the intended empirical distribution.

A useful local invariant is:

$$
\text{valid}(r_i, \mathcal{S}) = 1 \quad \Longrightarrow \quad r_i \text{ can be consumed by the next pipeline stage.}
$$

For `mixture`, the invariant should be explicit enough that a checker can fail fast. If
the invariant is only written in a notebook comment or an engineer's memory, it will not
protect a long-running data build.

Examples:
- A small local experiment can store this object in memory; a frontier-scale run must store it as sharded, versioned, validated records.
- The mathematical object is simple, but the operational contract must survive restarts, parallel workers, schema changes, and audits.
- The notebook for this section uses synthetic data so the same ideas can be executed without external files.

Non-examples:
- A path on disk without a manifest is not a reproducible dataset.
- A metric dashboard without record-level lineage is not a provenance system.
- A filter threshold without an audit sample is not evidence of quality.

Implementation consequence: every transformation should report both a count and a rate.
If $n_{\mathrm{in}}$ records enter the stage and $n_{\mathrm{out}}$ records leave, the
acceptance rate is

$$
a = \frac{n_{\mathrm{out}}}{n_{\mathrm{in}}}.
$$

A sudden change in $a$ is a data-drift signal even when the code still runs. This is why
pipeline math is inseparable from logging, manifests, and audit slices.

For LLM work, the token-weighted view is often more important than the document-weighted
view. A filter that removes 5 percent of documents may remove 30 percent of tokens if it
targets long documents. The corresponding token acceptance rate is

$$
a_{\mathrm{tok}} = \frac{\sum_i f(r_i)\,T_i}{\sum_i T_i},
$$

where $T_i$ is the token count or a deterministic token-count estimate. The distinction
matters for compute budgets, mixture proportions, and scaling-law interpretation.

## 7. Common Mistakes

| # | Mistake | Why It Is Wrong | Fix |
| --- | --- | --- | --- |
| 1 | Trusting a file because it exists | A zero-byte or unparsable artifact can still pass a loose path check | Validate content and parseability |
| 2 | Counting documents but not tokens | Long documents dominate compute | Report both document and token rates |
| 3 | Changing schemas without versioning | Old and new records become indistinguishable | Pin schema versions in every record |
| 4 | Dropping metadata during transforms | Audits and removals become impossible | Preserve source and transform lineage |
| 5 | Using nondeterministic ordering | Rebuilds cannot be compared | Seed and record ordering rules |
| 6 | Ignoring failed records | Silent loss can bias the corpus | Quarantine and summarize failures |
| 7 | Treating filters as neutral | Filters encode preferences and tradeoffs | Ablate and audit every major filter |
| 8 | Mixing train and eval sources | Evaluation becomes contaminated | Run overlap audits before release |
| 9 | Optimizing one aggregate score | Small domains can regress | Track slice metrics |
| 10 | Skipping data cards | Users cannot judge intended use or risk | Publish structured documentation |
| 11 | Assuming licenses are uniform | Source terms can conflict | Track license at source and record level |
| 12 | Forgetting reproducible manifests | The same name can refer to different data | Use hashes and version pins |

## 11. Mixture Optimization as Loss Minimization Over Simplices

A mixture is a probability vector over sources; training loss is a function of that vector, the token budget, and model scale (Sections 2-4).
Optimization therefore happens on a simplex with constraints: availability per source, repetition caps (Section 04), and slice floors for capabilities that must not regress.
Xie et al. (2023, DoReMi) optimize domain weights by training a small proxy model with group distributionally robust optimization, then transfer the weights to a larger run.
The transfer assumption — proxy-optimal weights help at scale — is empirical and must be checked per setting, not assumed.
Ye et al. (2024, Data Mixing Laws) fit functional forms predicting loss from mixture proportions, turning mixture choice into fitted optimization rather than grid search.
Liu et al. (2024, RegMix) similarly regress mixture-to-performance from many small runs to propose weights for the large run.

## 12. Proxy Models and What Transfers

Proxy runs are cheap stand-ins: smaller models, fewer tokens, same data pipeline (Section 5).
What transfers best is rankings of mixtures, not absolute losses.
A proxy too small may not exhibit the capability the mixture is meant to create; a proxy too large defeats the purpose.
Report proxy scale, token count, and the correlation between proxy and target outcomes on held-out mixtures.
If that correlation is weak in your setting, mixture optimization by proxy is astrology with GPUs.

## 13. Repetition, Availability, and Constraints

Mixture weights interact with finite availability: a 30% weight on a source holding 5% of tokens means six epochs over it (Section 04's realized-epoch arithmetic).
Repetition value decays (Muennighoff et al., 2023), so constrained optimization caps epochs per source and lets weights renormalize.
Licence and governance constraints (Section 06) enter as hard constraints, not preferences.
Quality tiers within a source can be treated as separate mixture components — often the highest-value refinement available.

## 14. Evaluation Design for Mixture Experiments

Mixture comparisons need fixed total tokens, fixed model, and fixed evaluation suites; varying any of them confounds the comparison.
Aggregate loss hides per-domain tradeoffs: report the slice losses the mixture was designed to move (Section 6).
Multiple seeds or bootstrap intervals separate mixture effects from run noise, especially at proxy scale.
A mixture that wins on average while failing a gated slice fails (Chapter 15's gate discipline applied to data).
Hold out mixture configurations from the fitting process to test whether a mixing law predicts rather than interpolates.

## 15. Curriculum and Annealing as Time-Varying Mixtures

A curriculum is a mixture that changes over training: domain phases, quality annealing, or late-stage upsampling of high-quality data.
Annealing on high-quality data near the end is widely reported to help, but it is a schedule claim and needs schedule ablations.
Time-varying mixtures complicate reproducibility: the schedule joins the assembly config (Section 04).
Checkpoint-conditional evaluation (which phase produced the gain) is the corresponding measurement.

## 16. Failure Modes of Mixture Optimization

Overfitting the proxy: weights tuned to proxy quirks or to the evaluation suite itself.
Goodhart collapse: one metric improves while unmeasured capabilities erode; slice gates are the defence.
Availability illusion: optimizing weights over tokens that dedup and filtering later remove (Sections 03, 05) — optimize over post-audit counts.
Scale surprise: a mixture optimal at 1B tokens misranks at 100B because domain losses scale differently; refit at increasing scale where possible.

## 18. Step-by-Step Worked Problems


**Problem 1: Spot the epoch trap.**
- A proposal sets papers to 30% of a 60B build from a 5B source.
- That is 18B sampled tokens, 3.6 epochs.
- Cap epochs, renormalize, and state the realized mixture (Section 13).

**Problem 2: Judge a proxy claim.**
- Proxy runs rank mixture A over B; at target scale the ranking flips on one slice.
- Transfer failed for that slice; report it and refit with target-scale points (Section 12).

**Problem 3: Design the comparison.**
- Two mixtures differ, but so do total tokens between runs.
- The comparison is confounded; fix the budget and rerun (Section 14).

**Problem 4: Anneal deliberately.**
- A schedule upsamples high-quality data in the final 10%.
- Ablate schedule versus constant mixture at equal tokens (Section 15).
- Attribute gains to phase with checkpoint evaluations.

**Problem 5: Defend against Goodhart.**
- Proxy loss improves while code-slice loss worsens.
- The gated slice vetoes the mixture (Section 16).

**Problem 6: Use post-audit counts.**
- Mixture weights were fit before dedup removed 25% of the web source.
- Refit over post-dedup availability (Sections 05, 16).

## 22. Worked Mixture Optimization (numbered protocol)

1. Inventory post-audit tokens per source and quality tier
2. Set epoch caps, slice floors, and licence constraints
3. Choose proxy scale and verify it exhibits the target capabilities
4. Sample candidate mixtures across the simplex, not only near the incumbent
5. Train proxy runs at fixed token budget for every candidate
6. Fit the response model or rank candidates with intervals
7. Test predictions on held-out mixture configurations
8. Check the winner against every gated slice
9. Transfer to the target run with a mid-scale confirmation if budget allows
10. Report intended and realized mixtures with the result

## 23. Within-Source Mixtures: Quality Tiers as Components

Splitting each source into quality tiers (Section 03 scores) multiplies the mixture's degrees of freedom usefully.
A common winning pattern is not 'more web' but 'less low-tier web, same high-tier web'.
Tier boundaries are scorer thresholds and inherit their calibration duties.
Report tier definitions with the mixture; weights over undefined tiers are meaningless.

## 24. Scale Dependence of Optimal Mixtures

Domain losses fall at different rates with scale, so the optimal mixture can drift as budget grows.
Mixing-law fits (Ye et al., 2024) make the drift explicit by including scale in the fitted function.
Practically: refit or at least re-rank leading mixtures when the token budget changes by an order of magnitude.
A mixture inherited from a smaller run is a prior, not a conclusion.

## 25. Mixture Decisions Under Uncertainty

Proxy estimates carry noise; choose mixtures that are robust across the plausible ranking set, not only the point winner.
Flat optima are good news: many mixtures perform alike, so pick the one respecting constraints and slice floors most comfortably.
Document the runner-up mixtures and why they lost; the next budget change may crown one of them.

## 26. Final Problems and Answers

1. **The optimal proxy mixture uses 5 epochs of a small source.** Repetition cap binds; renormalize and re-rank under the cap (Section 13).
2. **A mixing law predicts a mixture far outside the sampled region.** Treat as extrapolation: validate at proxy scale before trusting (Section 14).
3. **Aggregate improves, a gated language slice regresses.** Slice floor vetoes; adjust weights or add a constraint (Section 14).
4. **The anneal phase coincides with a learning-rate decay change.** Schedule effects are confounded; ablate one change at a time (Section 15).
5. **Weights were fit on pre-dedup counts.** Refit on post-audit availability before any training (Section 16).
